# Allocation, layout and garbage collection

## Reduce allocation churn

- Pre-size a slice when the result will be large enough for growth to matter and the expected size is reliable. Bound counts derived from input. Use `slices.Grow(s, extra)` when appending a known number of elements to an existing slice. Check both allocated bytes and retained capacity when estimates vary. [`slices.Grow`](https://pkg.go.dev/slices#Grow).
- Use a small local array for genuinely fixed-size scratch when the compiler keeps it on the stack. Check `go build -gcflags=-m=2 ./path/to/pkg` for escapes and inlining, then confirm `allocs/op`. A pointer, closure or interface conversion alone tells you little about whether a heap allocation happens. Large locals can escape due to size, and passing small values by value can be cheaper than adding indirection. [Go compiler diagnostics](https://go.dev/src/cmd/compile/README).
- Try caller-owned `dst []byte` append APIs or reuse local buffers across iterations. Document who owns the result and when a buffer may be reused. `bytes.Buffer.Reset` retains its backing buffer and `Bytes` aliases it until the next modification. Use `strings.Builder` for a string result and call `Grow` when useful. Avoid copying a non-zero builder. `strings.Builder.Reset` drops its backing buffer in the standard implementation. [`bytes.Buffer`](https://pkg.go.dev/bytes#Buffer), [`strings.Builder`](https://pkg.go.dev/strings#Builder).
- Compare `strconv.AppendInt`/`AppendUint` and `time.Time.AppendFormat` with intermediates on hot formatting paths. `fmt.Appendf` can preserve general formatting without returning an intermediate string. Use simple concatenation for short expressions and a builder or `strings.Join` when repeated concatenation copies the growing prefix. [`strconv`](https://pkg.go.dev/strconv).
- Go 1.25+ may place small variable-capacity `make` slice allocations on the stack. Go 1.26+ extends speculative stack-backed allocation to some `append`-grown slices, including short-lived intermediate backing arrays when the eventual result escapes. These are compiler decisions. Benchmark before adding manual stack buffers to avoid early growth allocations. [Go stack allocation optimizations](https://go.dev/blog/allocation-optimizations).

## Release retained memory deliberately

- `s[:0]` keeps the backing allocation and still permits reuse. For an exclusively owned slice of pointers or structs containing pointers, `clear(s)` before shrinking clears the current elements. Clear the obsolete tail during compaction while its previous length is still known. If an operation also has aliases, account for the mutation those aliases will observe.
- Starting with Go 1.22, `slices.Delete`, `DeleteFunc`, `Compact`, `CompactFunc` and `Replace` clear obsolete elements. Always use the returned slice. Preserve whether a return value is `nil` or empty when it matters to callers, for example when marshaling JSON. [Go slice functions](https://go.dev/blog/generic-slice-functions).
- A subslice or substring may keep the original allocation alive. Clone a small result when it outlives a much larger input, or before holding data from a reusable buffer. `slices.Clip` adjusts capacity without detaching storage. Use `bytes.Clone`, `strings.Clone`, or an explicitly allocated copy for a general slice. [Go slice retention](https://go.dev/blog/slices-intro), [`slices.Clip`](https://pkg.go.dev/slices#Clip), [`strings.Clone`](https://pkg.go.dev/strings#Clone).
- Start with one buffer per owner. Consider `sync.Pool` only for measured churn across independent callers. Pool pointers to mutable scratch objects, reset contents before reuse, and discard unusually large buffers based on the workload. Wait until downstream readers have finished with every alias before putting the buffer back. A pool can drop items at any time, so a miss must be cheap and every borrower must initialize its scratch. [`sync.Pool`](https://pkg.go.dev/sync#Pool).
- Test reuse under steady load and after a large request followed by idle time. Compare allocation rate, live heap and process RSS. Lower `B/op` can come with higher retained memory.

## Layout and locality

- Compare `[]T` with `[]*T` when many small records are separately allocated. Contiguous values can reduce allocation count, pointer chasing and GC scan work. Keep pointers where identity, independent lifetime or avoidance of large copies matters. Taking `&rows[i]` can retain the whole backing array, and growing `rows` may put subsequent elements in a different array.
- Go stores struct fields in declaration order with alignment padding. Inspect `unsafe.Sizeof`, `Alignof` and `Offsetof` on deployment architectures. Start with hot access and pointer layout, then consider reordering private, bulk-stored fields to shrink padding. Reordering can affect unkeyed literals, field order visible to reflection or encoders, and binary layout contracts. [`unsafe` size and alignment APIs](https://pkg.go.dev/unsafe), [Go size and alignment guarantees](https://go.dev/ref/spec#Size_and_alignment_guarantees).
- When GC scanning is a confirmed cost, put pointer-bearing fields toward the start of individually allocated objects where that reduces their scan prefix, or compare pointer-free records with bounded indices into a backing slice. Document index lifetime and handle stale indices if slots can be reused. Compare `/gc/scan/heap:bytes` as well as live bytes and access costs. [Go GC implementation guide](https://go.dev/doc/gc-guide#Implementation-specific_optimizations).
- Try a hot/cold split or parallel slices if a bulk scan touches a few fields of a wide record. Keep records together when the access pattern usually needs most fields. Test writes and random access too, since layouts that improve a read-only scan can complicate updates and worsen locality elsewhere.
- For repeatedly duplicated comparable values, consider `unique.Make` (Go 1.23+). Measure canonicalization cost, equality speed and live heap under realistic cardinality before introducing interning. [`unique`](https://pkg.go.dev/unique).

## Tune the GC after measuring churn and retention

1. Record process or container memory, request rate and tail latency alongside the runtime's `/gc/heap/live:bytes`, `/gc/heap/goal:bytes`, `/gc/heap/allocs:bytes`, `/gc/scan/heap:bytes` and `/cpu/classes/gc/total:cpu-seconds`. Use rates for cumulative metrics. [`runtime/metrics`](https://pkg.go.dev/runtime/metrics).
2. `GOGC` changes the heap growth target relative to live heap and roots. Higher values generally trade more memory for fewer collections. Lower values generally increase GC frequency. Compare defaults at steady load and during realistic spikes before choosing another setting.
3. `GOMEMLIMIT` (Go 1.19+) is a soft limit for Go-managed memory. Leave measured headroom for native allocations, mappings, other processes, and workload spikes. A very low limit can drive repeated GC and still be exceeded. Use process/container memory as well as Go's runtime metrics to verify headroom. [Go GC tuning guide](https://go.dev/doc/gc-guide).
4. Go 1.26 enabled Green Tea GC by default. On a GC-heavy workload, measure a supported toolchain upgrade against the current build. Compare GC CPU per unit of work as well as total CPU, memory and request latency. The release notes' 10–40% range refers to GC overhead in GC-heavy workloads. [Go 1.26 release notes](https://go.dev/doc/go1.26#runtime).
